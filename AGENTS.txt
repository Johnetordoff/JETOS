JETOS AGENT INSTRUCTIONS
========================

This file is authoritative guidance for humans and coding agents working in
this repository.

PROJECT IDENTITY
----------------
JETOS is an operating system whose normal implementation/control language is
JETOS Language: a directly editable fork of the latest STABLE CPython release.
It is not "Linux plus some Python scripts". Linux is current native substrate;
JETOS Language is intended to own as much operating-system behavior as can
correctly execute above that substrate.

PYTHON VERSION POLICY
---------------------
1. JETOS Language tracks the newest stable CPython feature/maintenance release.
2. Never pin JETOS to CPython main, alpha, beta, or release-candidate source.
3. When Python.org publishes a newer stable release, updating the pinned base is
   a priority maintenance change and should happen before unrelated release work.
4. Every Python-base update must pin an exact upstream commit and version.
5. Preserve JETOS patches as small, readable changes replayable on the next
   stable CPython release.
6. Current pinned stable base: Python 3.14.8, commit
   8e6e75d9102e39bed2a2b279203a396741180f12.

STANDARD-LIBRARY-ONLY RULE
--------------------------
1. JETOS-owned Python code may import only the Python/JETOS Language standard
   library and other JETOS-owned modules from this repository.
2. Do not add pip/PyPI runtime dependencies, requirements.txt, poetry, uv, conda,
   or vendored third-party Python packages for JETOS behavior.
3. tkinter is allowed because it is the standard-library GUI API. Its Tcl/Tk
   dependency is explicit native substrate.
4. Native libraries/external build tools are allowed only at documented native
   or bootstrap boundaries (kernel, compiler, libc, Tcl/Tk, QEMU, etc.).
5. If standard library code can implement something reasonably, start there.

PYTHON FIRST, NATIVE WHEN MEASURED
----------------------------------
1. If JETOS Language can do an operation correctly, implement it there first.
2. Measure before moving a hot path native.
3. A measured hot primitive may become a small readable C extension while its
   public control/API remains JETOS Language.
4. Native C extensions must be subinterpreter-safe where relevant.
5. Release the GIL around long-running native work when correct and beneficial.
6. Free-threaded builds may be evaluated with --disable-gil, but measurement and
   correct synchronization remain required.
7. New JETOS-owned C++ is prohibited. Imported C++ is migration debt.
8. Assembly is limited to architecture-required boundaries.

SUBINTERPRETER MODEL
--------------------
1. The main JETOS Language interpreter is the OS supervisor/interpreter.
2. Isolated subinterpreters are the preferred in-process service boundary when
   they improve ownership, failure separation, or parallelism.
3. Default granularity is one interpreter per capability/service domain.
4. One interpreter per physical device is allowed when measurement/isolation
   justifies it; it is not mandatory.
5. Use message passing and explicit immutable/copyable data between interpreters.
6. Subinterpreters are not a security sandbox.
7. Separate interpreter GILs plus separate OS threads may provide multi-core work.
8. Native extensions used by service interpreters must support multiple
   interpreters rather than assuming process-global Python state.

HARDWARE AND CAPABILITIES
-------------------------
1. Discover the machine; do not assume a laptop/desktop/server role from shape.
2. Preserve evidence for each discovered capability.
3. Distinguish exists / implementation installed / policy permits / active.
4. The desktop/app registry should be generated from discovered capabilities.
5. Terminal and System diagnostics remain universally available.
6. Prefer /sys, /proc, /dev, netlink, uevents, DRM/KMS, ACPI, and Device Tree over
   brittle command-output scraping.

DISPLAY/UI
----------
1. The standard JETOS GUI API is tkinter unless/until JETOS Language replaces it
   with another standard-library GUI API.
2. The reference desktop uses a Windows-95/98-era interaction/aesthetic language
   without Microsoft code/assets.
3. Never hard-code a commercial display resolution as a requirement.
4. Layout derives from actual display geometry and survives odd/custom sizes.
5. Keep layout policy separable from the renderer so geometry is headless-testable.
6. The long-term desktop/application UI may use HTML/CSS-like document markup as
   its interface description language so UI structure is easy to author, inspect,
   theme, and modify.
7. Core JETOS UI markup is rendered locally by the operating-system UI/runtime.
   It must not require ordinary HTTP requests, a remote web server, DNS, or an
   Internet connection merely to draw the desktop or a local application.
8. A browser-style rendering engine may be embedded or adapted as native/local
   display machinery. Treat the renderer as an OS component receiving local
   documents/state, not as evidence that JETOS itself is merely a web site.
9. Networking remains a separate capability and policy boundary from local UI.

VISUAL AND VM TEST LEVELS
-------------------------
1. Host GUI preview (`python jetos.py gui`) is the fastest renderer/layout test.
2. Docker+VNC (`python jetos.py gui-docker`) runs the actual Tk desktop in a
   reproducible Linux container and is the portable visual test for macOS,
   Windows, and Linux. It is NOT an OS-boot proof.
3. QEMU (`python jetos.py dev`) is the real guest-kernel/rootfs/PID-1 proof.
4. QEMU window/VNC modes may expose virtual display hardware, but do not claim the
   Tk guest desktop is working until the guest display backend actually starts it.
5. Keep these claims separate in PRs/tests: renderer works, container visual works,
   VM boots, guest display works, bare metal works.

PERSISTENT STORAGE AND ENCRYPTION
---------------------------------
1. Ordinary persistent JETOS data defaults to encryption at rest.
2. The global storage-encryption policy may be explicitly switched ON or OFF.
   OFF is a visible operator/development policy, never a hidden bypass.
3. Scoped path/domain overrides may explicitly require encryption or permit
   plaintext regardless of the global setting. Every override carries scope,
   reason, owner, and audit evidence.
4. Changing policy does not itself encrypt/decrypt an existing disk; it changes
   what JETOS requires and permits for that storage domain.
5. Do not invent a Python file cipher, AEAD construction, or KDF. Use reviewed
   native/kernel cryptography; dm-crypt/LUKS is the first implementation target.
6. Normal open/read/write/mmap APIs remain ordinary; cryptography is below the
   filesystem.
7. Plaintext in RAM is expected while data is actively used. Kernel page cache,
   tmpfs/ramfs/rootfs, interpreter objects, and memory caches may contain it.
8. Never add a secret attribute, magic filename, undocumented switch, or hard-coded
   secret that disables encryption.
9. /boot may be plaintext only for non-secret firmware-readable boot artifacts.
10. Keys never go in Git, source images, logs, or diagnostics. Key acquisition and
    recovery are separate boot-security boundaries.
11. Swap must be encrypted before enabling it; hibernation remains disabled unless
    its image is protected by the same at-rest model.
12. Storage status must be introspectable and production policy can fail closed.

IMAGE SIZE
----------
1. JETOS must measure rootfs, initramfs, kernel, and major contributors.
2. The current bootstrap guardrails are 128 MiB uncompressed rootfs and 48 MiB
   compressed initramfs; these are ceilings, not goals, and should ratchet down.
3. The lean profile may remove standard-library tests, demos, ensurepip, IDLE, and
   bytecode caches from the deployed image, while the full development tree stays
   editable/rebuildable outside the deployed image.
4. Do not remove runtime functionality blindly. Report largest files/directories,
   measure before/after, and preserve Tkinter/JETOS runtime requirements.

BOOT MEDIA AND INSTALLATION MODEL
---------------------------------
1. The normal JETOS product path is a machine or storage device already containing
   a bootable JETOS image: preloaded hardware, a preflashed disk, USB/flash media,
   or another directly bootable image. In that path there is no installation step;
   power-on should enter JETOS directly.
2. The bootable image is the canonical distribution artifact. Optimize it for a
   short, understandable boot path into the JETOS graphical desktop rather than
   requiring a conventional installer before the system can be used.
3. Installing/bootstrapping JETOS onto a machine that currently runs another OS is
   a secondary migration/development path, not the default experience.
4. Migration may support a dedicated target disk, explicit partition/dual-boot
   placement, or full-machine replacement, but every storage-changing operation
   must be deliberate, previewable, and explicitly approved by the user.
5. Never silently repartition, format, overwrite, or replace an existing operating
   system. Full replacement is the most aggressive mode and requires proven
   recovery/storage support plus an explicit request for that exact action.
6. Development hosts may continue to use Docker, VMs, QEMU, host GUI previews, or
   other non-destructive bootstrap environments without confusing those paths with
   the normal shipped/booted JETOS experience.
7. A preflashed image and an installed image should converge on the same runtime
   architecture, policies, desktop, and update model; installation is a way to put
   JETOS onto storage, not a different edition of the operating system.

BOOT AND BUILD
--------------
1. JETOS-owned build/orchestration logic is Python.
2. Generated kernels, imported upstream trees, root filesystems, and images live
   under .build/ and are not committed as opaque blobs.
3. Pin upstream inputs exactly.
4. Docker is an optional reproducible build/test environment, not JETOS architecture.
5. QEMU/hypervisors are test computers, not JETOS architecture.
6. Do not enable destructive bare-metal installation until recovery/storage paths
   are proven and the user explicitly requests it.

REPOSITORY HYGIENE
------------------
1. Keep source small, readable, inspectable, and deterministic.
2. README.md remains the single Markdown architecture document; use plain text for
   special machine/agent policy files such as this one.
3. No mysterious files, build steps, languages, or generated source blobs.
4. Run repository tests before claiming behavior works.
5. State execution boundaries honestly: implemented, static/unit tested,
   dry-run-tested, container-visual-tested, VM-boot-tested, and bare-metal-tested
   are different claims.
