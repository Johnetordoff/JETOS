JETOS NORMATIVE ARCHITECTURE CONSTITUTION
=========================================

STATUS
------
This document defines JETOS architectural invariants. MUST, MUST NOT, SHOULD,
SHOULD NOT, and MAY are normative. README.md, AGENTS.txt, implementation notes,
and build scripts may elaborate these rules but MUST NOT contradict them.

1. SYSTEM IDENTITY
------------------
1. JETOS is an operating system, not a Python application distribution on an
   otherwise opaque host OS.
2. JETOS Language is a maintained fork of stable CPython and is the normal
   high-level language for system logic, services, applications, policy,
   scripting, inspection, and interactive control.
3. Linux is the initial native kernel substrate. JETOS SHOULD move behavior into
   JETOS Language whenever it can execute correctly outside irreducible native,
   kernel, firmware, or hardware boundaries.
4. The intended boot path is firmware -> JETOS-selected kernel -> JETOS Language
   supervisor/userspace -> command line and graphical desktop.

2. PROGRAMMING MODEL
--------------------
1. JETOS has two first-class implementation languages:
   a. JETOS Language/Python for high-level work; and
   b. C for native code, ABIs, hardware/kernel boundaries, and measured hot paths.
2. Python C extensions SHOULD be the ordinary bridge between those layers.
3. New JETOS-owned C++ MUST NOT be introduced. Imported C++ is migration debt and
   SHOULD be replaced incrementally with readable C or JETOS Language where that
   change is technically justified and testable.
4. Assembly SHOULD be restricted to architecture-required boundaries.
5. JETOS does not ban binaries produced by other languages. Compatible binaries
   MAY execute when ABI, runtime, security policy, and capabilities permit it;
   JETOS simply does not promise those languages a first-class development stack.
6. A developer competent in Python and C SHOULD be able to understand and modify
   the normal JETOS-owned software stack without another implementation language.

3. UPSTREAM FORKS AND RECONCILIATION
------------------------------------
1. JETOS MAY be composed from maintained forks of mature upstream projects rather
   than rewriting them from first principles.
2. Every imported/forked component MUST identify its upstream repository, exact
   pinned revision, local patch set, build provenance, and licensing obligations.
3. A JETOS fork is not a frozen snapshot. It SHOULD continuously follow the chosen
   maintained upstream line while carrying only intentional JETOS divergence.
4. JETOS Language MUST track the newest stable CPython feature/maintenance release;
   prerelease CPython branches MUST NOT become the normal base.
5. Upstream security, correctness, portability, and performance improvements SHOULD
   be incorporated promptly unless they conflict with a deliberate JETOS invariant.
6. Local patches SHOULD remain small, readable, testable, and replayable. When an
   upstream change makes a patch unnecessary, that patch SHOULD be removed.
7. Merge conflicts are architectural decisions. Each conflict MUST be resolved by
   examining both semantics and choosing the result that best preserves deliberate
   JETOS invariants, compatible upstream improvements, testability, and minimum
   long-term divergence.
8. JETOS MUST NOT blindly choose "ours" or "theirs" for upstream conflicts.
   Judgment is required case by case; non-obvious decisions SHOULD record rationale.

4. SOURCE VISIBILITY AND KERNEL SOURCE
--------------------------------------
1. JETOS MUST distinguish JETOS-owned source, imported/forked source, and generated
   build artifacts.
2. Complete pinned upstream source used by a Fat system MUST be materializable and
   inspectable in an obvious source tree; generated binaries, root filesystems,
   kernels, caches, and images remain separate disposable build output.
3. Fat Mode MUST carry the editable JETOS source, the exact JETOS Language/CPython
   source, and the exact Linux kernel source corresponding to the running system.
4. Fat Mode SHOULD also retain the kernel configuration, JETOS kernel patches,
   symbols/debug metadata when available, and build provenance required to map the
   running kernel back to source and reproduce it.
5. Having complete kernel source does not imply unrestricted live kernel-memory
   access. Source visibility and runtime visibility are distinct properties.
6. Fat Mode SHOULD expose live kernel evidence through supported interfaces such as
   proc/sys filesystems, device/sysfs state, symbols where permitted, tracepoints,
   logs, scheduler/process state, mappings, and debug/instrumentation facilities.
7. JETOS MUST accurately report kernel state that is protected, unavailable, or
   unobservable in the current architecture/privilege configuration.
8. Skinny Mode MAY omit development source, but MUST retain exact provenance needed
   to reproduce the omitted source externally.
9. The provenance target is:

       source -> build rule -> artifact -> installed file -> image

   Unexplained operating-system files are defects.
10. Package-provided libc, Tcl/Tk, display libraries, crypto/compression libraries,
    toolchains, firmware, or similar boundaries MUST be reported as source debt or
    imported source until their exact source/provenance is incorporated.

5. EXECUTION, SUBINTERPRETERS, AND FREE THREADING
-------------------------------------------------
1. The main JETOS Language interpreter is the operating-system supervisor and MAY
   run as PID 1 after kernel/userspace handoff.
2. Isolated subinterpreters SHOULD be the normal in-process service/capability
   boundary when they improve ownership, failure separation, or parallelism.
3. Services SHOULD communicate through explicit message passing and narrow data
   contracts rather than accidental process-global state.
4. JETOS MUST NOT depend on one process-wide Global Interpreter Lock for correctness.
5. Free-threaded/GIL-disabled JETOS Language builds MUST be treated as a first-class
   test configuration as the required runtime and extensions support them correctly.
6. Native extensions used from multiple interpreters MUST be designed and tested
   for multiple-interpreter safety and correct synchronization.
7. Performance-sensitive operations SHOULD begin in readable JETOS Language and
   move to C only after measurement demonstrates a useful native boundary or hot
   primitive.

6. LIVE INTROSPECTION AND CONTROL
---------------------------------
1. Fat Mode MUST be designed as an inspectable operating system. JETOS Language and
   the graphical UI SHOULD expose structured state for services, interpreters,
   threads, mappings, buffers, devices, queues, files, storage, and capabilities.
2. Memory inspection SHOULD expose ranges, sizes, ownership, protections, backing
   objects/devices, and associated service/interpreter where available.
3. The graphical inspector SHOULD visualize memory and other resources geometrically,
   not only as hexadecimal text.
4. Where a mapping is writable and JETOS has authority, an explicit privileged mode
   MAY mutate individual bytes or bits. Such mutation MUST be opt-in, auditable,
   and visibly distinct from read-only inspection.
5. JETOS MUST NOT claim access to protected, unavailable, or physically unobservable
   state. Hardware, MMU, kernel, privilege, and security boundaries remain real.
6. The Python console and graphical inspector SHOULD be two views of the same
   capability APIs; the GUI SHOULD NOT depend on hidden control paths.

7. USER INTERFACE AND COMMAND LINE
----------------------------------
1. JETOS MUST provide a command-line/interactive JETOS Language control path.
2. JETOS SHOULD provide a graphical desktop and system-inspection interface.
3. The reference interaction style is fast, simple, and legible, using a Windows
   95/98-era interaction vocabulary without Microsoft code/assets.
4. The long-term UI MAY use HTML/CSS-like document markup for authorability and
   theming, but local rendering MUST NOT require HTTP, DNS, a remote web server, or
   the public Internet merely to display the desktop or a local application.
5. A browser-style renderer, if used, is local OS display machinery rather than a
   claim that JETOS is a website.
6. UI layout MUST derive from actual display geometry rather than a fixed resolution.

8. FAT MODE AND SKINNY MODE
---------------------------
1. Fat Mode and Skinny Mode are deployment profiles of the SAME JETOS version and
   source lineage, not separate editions or forks of JETOS.
2. Fat Mode is the general-purpose personal-computer/developer profile. It SHOULD
   carry source, tests, compilers/build tools, inspection surfaces, and enough native
   development support for in-place operating-system development.
3. Fat Mode is a general-purpose application host: it SHOULD be able to run any
   application compatible with its ABI, available runtimes, capabilities, and
   security policy rather than being restricted to a fixed appliance application set.
4. Skinny Mode is the target/device/application profile. It MAY remove source trees,
   compilers, tests, demos, caches, and general-purpose development facilities.
5. A Skinny image SHOULD declare the applications and capabilities it is intended to
   run. It need not support arbitrary application installation/execution beyond that
   target set.
6. Fat Mode MUST be able to derive, build, and program/flash Skinny images from its
   own source tree. Designing on Fat and deploying a target-specific Skinny image is
   a normal JETOS workflow.
7. A Skinny image derived from Fat MUST preserve the JETOS release/version identity,
   source revision/provenance, public runtime semantics, and capability model of the
   source Fat system; only packaging, included source/tooling, enabled capabilities,
   target applications, and hardware-specific artifacts may differ.
8. Fat Mode MAY be used in production when live development or deep inspection is
   desired. "Production" and "Skinny" are not synonyms.
9. Image size MUST be measured in both profiles. Skinny SHOULD enforce strict size
   budgets; Fat SHOULD optimize size without deleting its defining source/tooling.
10. The canonical names are "fat" and "skinny". "full" and "lean" MAY remain only
    as compatibility aliases during migration.

9. BOOT, DISTRIBUTION, AND INSTALLATION
---------------------------------------
1. The canonical JETOS product artifact is a directly bootable image.
2. The normal path is preloaded/preflashed media: power on -> JETOS. A conventional
   installer is not required for this path.
3. USB/flash media, dedicated disks, virtual disks, and Raspberry Pi SD cards MAY
   carry the image.
4. Installing JETOS onto a machine already running another OS is a secondary
   migration/development path.
5. JETOS MUST NOT silently repartition, format, overwrite, or replace an existing
   operating system. Storage-changing migration MUST be previewable and explicitly
   authorized for the selected target.
6. Full-machine replacement MUST require proven recovery/storage behavior plus an
   explicit request.
7. Docker, QEMU, VMs, host previews, and similar systems are development/test
   mechanisms, not the architectural identity of JETOS.

10. STORAGE, CAPABILITIES, AND HOST BOUNDARIES
----------------------------------------------
1. ext4, FAT, tmpfs, and other filesystems are implementations, not JETOS identity.
   JETOS SHOULD express required storage semantics through narrow interfaces.
2. Constrained targets MAY omit/substitute capabilities when the loss is explicit.
3. Persistent JETOS data SHOULD default to encryption at rest using reviewed native
   or kernel mechanisms; JETOS MUST NOT claim encryption when it is not present.
4. Hardware/services SHOULD be represented as explicit capabilities with evidence,
   implementation availability, policy permission, and active state.
5. Networking is a capability boundary independent of the local UI; JETOS SHOULD
   support configurations where networking is physically or verifiably off.
6. JETOS MUST NOT require jailbreaking iPhone/iPad or bypassing host security.
7. When JETOS coexists with another local system such as MacBrain, interaction
   SHOULD use explicit local/network/versioned-artifact interfaces rather than
   silently rewriting the other system's live root.

11. GIT AND LIVE DEVELOPMENT
----------------------------
1. Git is the authoritative history of JETOS-owned source and SHOULD be a first-class
   Fat Mode development mechanism.
2. Running JETOS MAY update userspace from Git only through a path that validates
   cleanliness, fetches the intended revision, rejects unsafe history changes by
   default, runs relevant tests, and reloads/restarts only after validation.
3. Userspace Git updates MUST NOT be represented as equivalent to replacing
   firmware, partition layout, kernel, or other pre-userspace components requiring
   rebuild/reboot/reflash.

12. TESTING, SMALLNESS, AND BENCHMARKING
---------------------------------------
1. JETOS MUST distinguish implementation from proof. Source review, unit tests,
   host GUI preview, container visual tests, VM boot, guest graphical boot, and
   bare-metal boot are distinct evidence levels and MUST NOT be conflated.
2. A claim that something works MUST identify the strongest environment in which it
   has actually executed successfully.
3. Repeatable tests SHOULD cover free-threading, subinterpreters, storage policy,
   source provenance, image size, architecture-specific behavior, Fat-to-Skinny
   derivation, and application/capability restrictions.
4. Smallness is an operating-system feature. JETOS SHOULD minimize source lines,
   duplicated concepts, boot work, runtime dependencies, and image size without
   sacrificing clarity or correctness.
5. Code golf is not a goal. Explicit types, clear names, dataclasses/structured
   records, narrow interfaces, and readable control flow are preferred.
6. Performance decisions MUST be benchmark-informed. Comparable before/after
   measurements SHOULD precede moving work to C or increasing native complexity.
7. JETOS SHOULD continuously measure source-language composition, annotation
   coverage, image size, boot/runtime performance, and remaining C++ migration debt.

13. CHANGE GOVERNANCE
---------------------
1. Architecture changes SHOULD be explicit reviewed changes to this constitution or
   a subordinate specification that cites its governing rule.
2. Implementations MAY evolve aggressively; invariants SHOULD change deliberately.
3. When reality contradicts this document, maintainers MUST fix the implementation
   or amend the constitution. Silent drift is not acceptable.
4. JETOS prioritizes inspectability, reproducibility, explicit authority, and
   deliberate engineering judgment over hidden automation or accidental complexity.
