JETOS NORMATIVE ARCHITECTURE CONSTITUTION
=========================================

STATUS
------
This document defines JETOS architectural invariants. MUST, MUST NOT, SHOULD,
SHOULD NOT, and MAY are normative. GEN2.txt is the active generation profile
and may further narrow these rules, but may not weaken safety or truthfulness.

1. SYSTEM IDENTITY
------------------
1. JETOS is an operating system, not a Python application distribution.
2. JetOS Python is JETOS's normal high-level operating-system language and runtime.
   Its historical seed does not define its current identity.
3. JETOS C/native source provides kernel, runtime, ABI, hardware, and measured
   low-level implementation beneath JetOS Python.
4. The intended Gen2 boot path is firmware/hypervisor -> JETOS kernel -> Gen2
   userspace -> JetOS Python supervisor/PID 1 -> JETOS command shell.
5. Graphical interface behavior belongs to the separate Decaptor layer and MUST
   NOT be required for the command-line operating system to boot and function.

2. PROGRAMMING MODEL
--------------------
1. JETOS has two first-class implementation languages:
   a. JetOS Python for policy, shell, services, orchestration, applications,
      introspection, and user-programmable behavior; and
   b. C for native runtime/kernel/ABI/hardware work and measured hot primitives.
2. Assembly MAY be used only where an architecture requires it.
3. New JETOS-owned C++ MUST NOT be introduced as a preferred implementation.
   C++ present in admitted source is migration debt and SHOULD be replaced with
   readable C or JetOS Python when behavior can be preserved and tested.
4. Compatible binaries produced by other languages MAY execute when JETOS has the
   required ABI/runtime/capability support, but JETOS does not owe those languages
   first-class development stacks.
5. A developer competent in JetOS Python and C SHOULD be able to understand and
   modify the normal JETOS-owned software stack.

3. FROZEN GENERATIONS AND SOURCE INTAKE
---------------------------------------
1. A JETOS generation is a frozen source generation.
2. A component enters a generation only after a deliberate source snapshot is
   copied into the JETOS generation tree and admitted by review.
3. After intake, the copied files are JETOS source. Normal build, boot, testing,
   diagnostics, and user-facing code MUST NOT follow external branches, release
   feeds, package-manager freshness, or remote repositories to decide what the
   generation contains.
4. Historical origin, revision, license, and provenance facts MAY be retained in a
   sealed archival record. They are evidence about intake, not active dependency
   relationships or runtime identities.
5. A new external release does not update a JETOS generation. JETOS changes only
   when maintainers deliberately admit source and reseal the generation.
6. Missing capabilities are source-debt items. The preferred progression is to
   admit the exact required implementation into JETOS rather than create an
   indefinite live dependency.
7. Existing frozen generations MUST remain reproducible and inspectable even when
   later generations admit different source.

4. SOURCE VISIBILITY, SEALING, AND BUILD OUTPUT
-----------------------------------------------
1. Gen2 canonical source lives under the generation tree and MUST be inspectable as
   ordinary files.
2. The Gen2 source seal MUST record each admitted ordinary file by path, size, and
   cryptographic digest or equivalent deterministic integrity evidence.
3. Normal Gen2 build/boot MUST verify the seal and MUST fail rather than silently
   fetching missing source.
4. Compilation and configuration SHOULD operate on separate build/work trees so a
   normal build does not mutate the sealed canonical source.
5. Generated binaries, objects, kernels, root filesystems, caches, and images are
   disposable build artifacts and MUST remain distinguishable from source.
6. Unexplained operating-system files are defects. JETOS SHOULD preserve a mapping:

       admitted source -> build rule -> artifact -> installed file -> image

7. Host/compiler/libc/toolchain/framework requirements not yet admitted to Gen2
   MUST be reported honestly as source/build debt.

5. COMMAND-LINE-FIRST OPERATING SYSTEM
--------------------------------------
1. Gen2 is command-line-first.
2. The command shell MUST be a real JETOS boot destination, not a host-side demo.
3. The shell SHOULD provide direct file navigation/inspection, machine/system
   introspection, program launching, and access to JetOS Python.
4. JetOS Python MUST remain directly reachable from the command shell without
   making ordinary file/application operations require Python syntax.
5. The command-line environment SHOULD be small, direct, and legible in the spirit
   of classic DOS-era operating environments while remaining a modern JETOS design.
6. JETOS SHOULD be able to launch compatible applications directly from this shell.

6. JETOS PYTHON
---------------
1. JetOS Python is operating-system source, not an opaque third-party runtime.
2. Parser/compiler/runtime/object-model/GC/import/stdlib behavior MAY be edited as
   JETOS evolves.
3. JetOS Python MUST identify itself as JETOS at runtime.
4. Gen2 runtime identity MUST NOT depend on or advertise a historical seed version
   as though that seed were the current platform identity.
5. JetOS Python SHOULD own high-level system semantics; C should implement native
   boundaries and measured primitives rather than duplicate policy unnecessarily.
6. JETOS MUST NOT depend on one process-wide Global Interpreter Lock for correctness.
   Subinterpreters/message passing and free-threaded operation remain important
   test directions when technically correct.

7. KERNEL, CPU, REGISTERS, AND INTROSPECTION
--------------------------------------------
1. The admitted JETOS kernel source MUST include the architecture-specific CPU,
   register, trap/exception, interrupt, MMU, scheduler, memory, driver, and boot
   implementation required by the target.
2. Fat/developer JETOS SHOULD make these files searchable and inspectable locally.
3. JETOS SHOULD expose runtime kernel evidence through supported mechanisms such as
   proc/sys filesystems, device/sysfs state, logs, mappings, scheduler/process state,
   symbols/debug metadata, and trace facilities where available.
4. Source visibility does not imply unrestricted live-memory authority. JETOS MUST
   report protected/unavailable state accurately.
5. Explicit privileged byte/bit mutation MAY exist only when JETOS genuinely has
   authority; such mutation MUST be opt-in, auditable, and visibly distinct from
   read-only inspection.

8. DECAPTOR
-----------
1. Decaptor is the JETOS graphical/interface layer.
2. Decaptor MUST be separable from the command-line boot proof.
3. Decaptor SHOULD consume the same capability APIs used by command-line and JetOS
   Python control surfaces rather than invent hidden parallel authority paths.
4. Local graphical rendering MUST NOT require public Internet access merely to
   display the desktop or a local application.
5. Display layout MUST derive from actual display geometry.

9. DEPLOYMENT PROFILES
----------------------
1. Fat Mode and Skinny Mode are profiles of the SAME JETOS generation/source lineage.
2. Fat Mode is the developer/personal-computer profile and SHOULD carry source,
   introspection surfaces, and enough tooling for in-place development.
3. Skinny Mode MAY omit source/development payload but MUST retain enough generation
   identity/provenance to reproduce its omitted source from the corresponding Fat tree.
4. Fat Mode MUST be able to derive target-specific Skinny images from its own JETOS
   generation source.
5. Image size SHOULD be measured in both profiles; Skinny MAY enforce stricter budgets.

10. BOOT, DISTRIBUTION, AND HOST BOUNDARIES
-------------------------------------------
1. The canonical JETOS product artifact is directly bootable media/image.
2. JETOS MUST NOT silently repartition, format, overwrite, or replace an existing OS.
3. Docker, QEMU, VMs, host previews, package managers, and host operating systems are
   bootstrap/development mechanisms when used; they are not JETOS identity.
4. Any such external build-host machinery that remains necessary for Gen2 MUST be
   listed as build debt rather than described as internalized JETOS source.
5. Networking is an independent capability and MAY be verifiably off.
6. JETOS MUST NOT require bypassing host platform security to coexist with another OS.

11. STORAGE AND CAPABILITIES
----------------------------
1. Filesystems are implementations, not JETOS identity.
2. Hardware/services SHOULD be represented as explicit capabilities with evidence,
   implementation availability, policy permission, and active state.
3. Persistent data SHOULD default to encryption at rest using reviewed native/kernel
   mechanisms when that capability is present; JETOS MUST NOT claim encryption when
   it is absent.
4. Constrained targets MAY omit capabilities when the loss is explicit.

12. TESTING, SMALLNESS, AND PERFORMANCE
---------------------------------------
1. JETOS MUST distinguish source review, structural tests, build success, VM boot,
   guest command-shell proof, graphical proof, and bare-metal proof.
2. A claim that something works MUST identify the strongest environment in which it
   actually executed successfully.
3. Smallness is an operating-system feature, but code golf is not a goal.
4. Performance changes SHOULD be benchmark-informed.
5. JETOS SHOULD measure source-language composition, image size, boot/runtime
   performance, and remaining C++ migration debt.
6. Guard tests SHOULD fail if Gen2 silently regains live source fetching, external
   freshness checks, a mandatory graphical boot path, or external runtime identity.

13. CHANGE GOVERNANCE
---------------------
1. Architecture changes SHOULD be explicit reviewed changes to this constitution or
   the active generation specification.
2. Implementations MAY evolve aggressively; invariants SHOULD change deliberately.
3. When reality contradicts this document, maintainers MUST fix the implementation
   or amend the constitution. Silent drift is not acceptable.
4. JETOS prioritizes inspectability, reproducibility, explicit authority, frozen
   evidence, and deliberate engineering judgment over hidden automation.
